# PERF — оптимизация рендера боя без потери визуала (этапы PF-0…PF-6)

Профилактическая оптимизация: жалоб на тормоза нет, это перестраховка. Цель — снять лишнюю нагрузку на слабом Android (60 FPS при 600 юнитах и ~20 узлах) и **ничего не менять во внешнем виде**. Логика `src/core/` не трогается.

## Правила
- Каждый этап — **отдельный коммит** (сообщение на английском, префикс `perf:`), после каждого `npm run lint && npm run test && npm run build`.
- Визуал неизменен. Допустима разница в цифрах узла на уровне субпикселя (см. PF-2). До первого изменения (PF-0) снять эталонные скриншоты, после каждого этапа сверять.
- Не оптимизировать вслепую: решение о каждом этапе опирается на замер из PF-0. Если этап не даёт заметного выигрыша — не делать, записать это в таблицу результатов внизу.
- Правило из CLAUDE.md №7 действует: в бою никаких аллокаций в горячем пути, никаких `Text`/`Graphics` на юнита.
- Если что-то неясно по визуалу или есть выбор, меняющий внешний вид, — спросить, а не решать самому.

## Что уже сделано (не переделывать)
- Число узла обновляется не чаще раза в `NODE_VIEW.refreshMs` (250 мс) и только при смене `floor(troops)` (`DisplayFilter` + `drawnCount`).
- Тело узла (`NodeView.drawBody`) перерисовывается только при смене ключа; дуга вместимости квантуется до 48 шагов.
- Юниты — один `Blitter` с пулом.

## Гипотезы (проверить замером в PF-0)
1. `Phaser.GameObjects.Text` со stroke на каждом узле: каждый `setText` = перерисовка canvas + загрузка текстуры в GPU. Плюс отдельная текстура на узел ломает батчинг вместе с `Blitter`.
2. `capGfx` (`Graphics.clear()` + 2 `arc`) перерисовывается до 48 раз за заполнение узла.
3. Аллокации каждый кадр: `Object.values(world.nodes)` в `BattleScene.render`, строка-ключ `` `${owner}|${kind}|…` `` в `NodeView.sync`, строка-ключ в `syncCapacity`.
4. `drawDragLines`, `drawSendBadge`, `drawGoal`, `hud.update` вызываются каждый кадр и могут делать лишний `clear()`/`setText`.

## PF-0. Замер (без изменений кода игры)
- Скрипт `scripts/profile-battle.mjs` (Playwright/Chromium, который уже есть в окружении; если нет — `performance.now()`-инструментация под dev-флагом): запускает `dev_stress` и 1–2 реальных уровня главы 1, CPU throttling ×6 (CDP `Emulation.setCPUThrottlingRate`), 30 с боя.
- Снять: средний/p95/p99 время кадра, число draw call'ов (`renderer.drawCount` или аналог в Phaser 4 — проверить), время `NodeView.sync` + `render()` суммарно за кадр (замер через `performance.now()` вокруг цикла по узлам), число вызовов `Text.setText` и `Graphics.clear` в секунду, аллокации/GC (Performance trace, minor GC в секунду).
- Эталонные скриншоты: портрет 360×640 и альбом 1280×720, один и тот же seed/момент боя (детерминированная симуляция позволяет остановиться на фиксированном тике), положить в `docs/perf/baseline/` (не в билд).
- Итог — таблица «до» внизу этого файла. Коммит: скрипт + эталоны.
- **Готово, когда:** есть воспроизводимая команда `npm run profile` и таблица «до».

## Порядок после PF-0 (решение пользователя, 2026-11-07)
По замеру почти весь кадр — перестройка `Graphics` внутри Phaser (см. «Итоги PF-0»), поэтому порядок такой: **PF-G** (фон и дороги в текстуру) → **PF-5** (тела узлов в текстуру) → PF-1…PF-4 и PF-6 — только если после них ещё есть заметный выигрыш.

## PF-G. Фон и дороги — одна запечённая текстура (добавлен после PF-0)
- Луг (`drawMeadow`) и дороги (`RoadView`) за бой не меняются: перерисовываются только в `relayout` (смена размера). Сейчас это два `Graphics` на 4 500 + 1 300–2 600 команд, которые Phaser перестраивает каждый кадр.
- Оба рисуются как сейчас, но в `Graphics` вне списка отображения, и при `relayout` запекаются в одну `DynamicTexture` размером с экран (WebGL, тот же конвейер, что и кадр; не `generateTexture` — он рисует через canvas 2D, края были бы другими). На экране — одна `Image` на месте фона, в том же порядке слоёв.
- **Готово, когда:** скриншоты `c01_l06` и `c01_l09` (портрет и альбом) совпадают с эталонами `docs/perf/baseline/` (допускается разница сглаживания краёв, не допускаются сдвиги и смена цвета); в замере пропали два самых тяжёлых `Graphics`.

## PF-1. Аллокации в кадре (самое безопасное)
- `BattleScene.render`: массив узлов (`Object.values`) строится один раз при загрузке уровня/relayout, а не каждый кадр. Так же — в других местах, где та же конструкция в `update`.
- `NodeView.sync` / `syncCapacity`: вместо строки-ключа сравнивать поля напрямую (хранить прошлые `owner`, `kind`, `size`, `building type/level`, `hasGoldVein`, `radius`, `fill`, `over`, `capacity`, `showCap` как отдельные поля или как одно число-маску). Поведение (когда перерисовывается) не меняется.
- **Готово, когда:** в Performance trace в `render()` нет аллокаций в установившемся бою; скриншоты идентичны побайтово.

## PF-2. Счётчик узла без `Text`
- Заменить `countText` (и `capText`, если замер покажет выигрыш) на цифры из **заранее запечённого атласа**: цифры 0–9 тем же шрифтом, размером и обводкой, что даёт `textStyle` + `setStroke` в `place()`. Число собирается из спрайтов (`Blitter`/`Image` из одной текстуры, без canvas и без загрузки в GPU при смене числа). Атлас запекается при загрузке (BootScene, см. PF-6) и заново — только при смене размера раскладки.
- Выравнивание, размер (`radius * 0.66`, минимум `px(15)`), толщина обводки (`radius * 0.14`), цвет — как сейчас. Числа вида «/35» (`capText`) — по результатам замера: показывается только на выбранном узле, возможно, оставить `Text`.
- Если для совпадения с `Text` нужен нестандартный шаг (кернинг, межцифровой интервал), подогнать так, чтобы разница была не заметна глазу; если не получается — спросить.
- Сравнить скриншоты: допускается разница сглаживания краёв цифр, не допускаются сдвиги, смена размера/толщины/цвета.
- **Готово, когда:** при росте числа не происходит перерисовок canvas (`Text.setText` вне HUD не вызывается в бою), draw call'ов не больше, чем до этапа.

## PF-3. Дуга вместимости без `Graphics.clear()`
- Варианты в порядке предпочтения: (a) предзапечённое кольцо-текстура на размер узла + маска/`setCrop`/сегменты с `setVisible`, (b) один `Graphics`, но перерисовка только при смене шага. Выбрать по замеру из PF-0. Шаг квантования 48 не менять, если нет явной причины (визуал!).
- Цвет (обычный/золотой при перезаполнении), толщина (`max(px(3), r*0.1)`), стартовая точка (−π/2) и прозрачность фонового кольца — прежние.
- **Готово, когда:** вызовов `Graphics.clear()` для дуг в установившемся бою нет, скриншоты совпадают.

## PF-4. HUD, линии свайпа, цель, бейдж отправки
- По замеру: `drawDragLines` / `drawSendBadge` / `drawGoal` / `hud.update` — не вызывать `clear()`/`setText`, если состояние не изменилось (флаг/ключ «грязно»). Пока свайпа нет, `drawDragLines` выходит сразу (проверить, что и `clear()` не вызывается повторно, если линии уже очищены).
- `BattleHUD.update`: `setText` только при смене значения (золото, темп, секунды заклинаний) — часть уже так, проверить остальное.
- **Готово, когда:** в бою без ввода игрока эти функции не делают ни одного `clear()`/`setText` за кадр.

## PF-5. Статичный слой узлов (только если после PF-1…4 есть смысл)
- Тело узла (круг, значки, корона, золото) в `RenderTexture` или кэшированную текстуру на узел, перерисовка при смене ключа тела. Делать **только если** по замеру `Graphics`-тела остаются заметной долей кадра. Иначе пропустить и записать «не требуется».

## PF-6. Прогрев при загрузке (BootScene)
Загрузочный экран сам по себе игру не ускоряет, но выносит разовую работу из боя, чтобы в нём не было «фризов» на первом кадре:
- запекание атласа цифр (PF-2) и текстур юнитов (`generateTexture`) — в `BootScene`, до `LoadingAPI.ready()`;
- прогрев пула `Blitter`/`Bob` на максимум юнитов, который ожидается (по `STRESS_UNITS`/вместимости уровня), чтобы в бою пул не рос;
- предзагрузка и декодирование звуков/музыки текущей главы (`docs/AUDIO.md`), загрузка шрифтов до первого `Text`;
- пустые прогоны шейдеров/`DisplayFilter` не нужны.
Отдельный видимый экран с индикатором добавлять **только если** прогрев длится дольше ~0.5–1 с на слабом устройстве; иначе достаточно существующего `BootScene`. Помнить про требование Яндекс Игр: `LoadingAPI.ready()` вызывать, когда всё готово.
- **Готово, когда:** первый кадр боя не длиннее среднего кадра более чем в 2 раза (по замеру PF-0).

## PF-7. Просадка FPS (60 → ~50) при получении кристаллов на экране результата
Жалоба игрока: на победе, когда кристаллы летят к счётчику, FPS падает с 60 до ~50. Это единственный подтверждённый симптом, поэтому **PF-0 обязан снять профиль именно этого момента** (от появления панели результата до конца счёта), и этап делается рано — сразу после PF-1.

Гипотезы (`src/scenes/BattleHUD.ts`: `showResult`, `flyCrystals`; `BattleScene.showResult`) — проверить замером, не угадывать:
1. **`text.setText(...)` каждый кадр** в `onUpdate` твина счёта: `Text` со stroke перерисовывает canvas и грузит текстуру в GPU ~каждый кадр на протяжении `(count-1)*flyStaggerMs`. Лечение: обновлять текст только при смене `Math.round(shown.value)` (сейчас вызывается безусловно), а при необходимости — цифры из атласа (PF-2).
2. **До 8 новых `Graphics` + `drawCrystal` в момент старта полёта**, затем `destroy()` каждого. Лечение: один раз запечь текстуру кристалла (`generateTexture`) и летать `Image`'ами из пула на 8 штук, без `Graphics` и без `destroy()` в анимации.
3. **Пульс иконки счётчика** (`tweens.add({scale…yoyo})`) создаётся на каждое приземление — до 8 твинов подряд; и `icon.setPosition` каждый кадр. Лечение: один твин/без повторного создания, позицию менять только когда меняется `text.width`.
4. **Сцена боя продолжает рендериться под полупрозрачной панелью**: `BattleScene.render` каждый кадр синхронизирует все узлы, юниты, HUD, хотя бой окончен. Лечение: после конца боя не вызывать `sync`/`units.render` для неизменного состояния (или один раз отрисовать финальное состояние и дальше пропускать), оставить только то, что реально анимируется.
5. **Совпадение по времени с джинглом** (`playJingle` в `RESULT_DELAY_MS`): первое декодирование mp3 / создание аудио-узлов может дать фриз в тот же кадр. Лечение: декодировать джинглы заранее (PF-6), в замере отделить аудио от графики (прогон с выключенным звуком).
6. `Container` с `alpha`-твином (`fade`) на весь оверлей, пока в нём десятки `Text`/`Graphics`: возможна доп. композиция. Проверить, отключив fade в замере.

- Порядок: замерить → поочерёдно отключать гипотезы (по одной, с флагом) и смотреть p95/p99 кадра → чинить только подтверждённое. Один коммит на одну причину.
- Визуал тот же: количество летящих кристаллов, тайминги (`RESULT_PANEL`), счёт «до → после», пульс иконки.
- **Готово, когда:** при CPU throttling ×4 на экране результата нет кадров дольше ~20 мс (p99), на `dev_stress` и обычном уровне; в таблице результатов есть «до/после».

### Итоги PF-0 (2026-11-07)

**Как мерили.** `npm run profile` (`scripts/profile-battle.mjs` + `src/dev/profiler.ts`, включается только `?profile` на dev-сервере, в сборку не попадает): Edge headless с настоящей видеокартой (AMD Radeon 780M, D3D11), CPU throttling ×6, 1280×720, 4 с прогрева и 30 с замера на уровень; сырые числа — `docs/perf/pf0-before.json`. Эталонные скриншоты на тике 200 — `docs/perf/baseline/` (`npm run profile -- --shots`).

**Главный вывод: почти всё время кадра — перестройка `Graphics` внутри Phaser, а не наш код.** В Phaser 4 каждый `Graphics` в WebGL каждый кадр заново проходит свои команды и строит треугольники (`GraphicsWebGLRenderer`: новые `Path`/`Point` на каждый кадр), даже если ничего не менялось. Отсюда и время, и мусор:
- `dev_stress`: кадр 171 мс работы, из них отрисовка Phaser 157 мс, из неё `Graphics` 142 мс (66 объектов, 16 350 команд за кадр). Весь наш `update` (симуляция + `render()` + узлы + юниты) — 13 мс.
- `c01_l06`: работа 53 мс, `Graphics` 41 мс (23 объекта, 8 600 команд); наш код — 3 мс.
- Аллокации 56–75 МБ/с при ×6 (12 minor GC в секунду) — в основном те же пути `Graphics`; наши аллокации на этом фоне не видны.

**Самые тяжёлые `Graphics`** (`window.__profile.graphicsTop()`): фон-луг — 4 500 команд, дороги — 1 300–2 600, тела узлов — 250–550 команд каждый (на `dev_stress` 20 узлов × 405), кнопки HUD ~220. Фон и дороги за бой не меняются вовсе, тела узлов — редко.

**Что это значит для этапов.**
- Гипотезы 1–4 подтвердились только частично и весят мало: `Text` перерисовывается 6–34 раз в секунду, `Graphics.clear` 14–37 раз в секунду, наш `render()` — 2–10 мс из 50–170.
- Основной выигрыш — **запечь неизменные `Graphics` в текстуры** (одна картинка вместо тысяч команд за кадр): фон и дороги, затем тела узлов (это PF-5, который по плану стоит последним и «только если»). Это меняет порядок этапов и добавляет новый (фон и дороги в плане нет) — **решение за пользователем**, см. вопрос в ответе к PF-0.
- Визуал при запекании должен совпасть: текстура рисуется в том же разрешении (game px = пиксели экрана), сравнение — с эталонами в `docs/perf/baseline/`.

### Итоги PF-G (2026-11-07)
- Фон и дороги рисуются в `Graphics` вне списка отображения и запекаются в одну текстуру размером с экран (`src/view/BakedLayer.ts`) при `relayout`.
- **Через canvas 2D, а не WebGL.** Первая попытка — `DynamicTexture` (WebGL): в Phaser 4 рисование в текстуру идёт без MSAA, края дорог и травы вышли «лесенкой» — видимое изменение. Через canvas 2D (`Graphics.generateTexture` в один canvas) края сглажены: отличие от эталона только в сглаживании краёв (до 23 из 255 по яркости на отдельных пикселях краёв, сдвигов и смены цвета нет; сверка — `npm run profile -- --shots --dir docs/perf/after --compare docs/perf/baseline`).
- **Выигрыш скромный (~8 % кадра на уровне 6), и это важный вывод для следующих этапов:** время `Graphics` в Phaser 4 почти не зависит от числа команд — у каждого объекта большая постоянная цена (~2,5–3 мс при ×6; `Graphics` из 28 команд стоит столько же, сколько из 250). Видно по времени на объект (`window.__profile.graphicsTop()`): на `dev_stress` каждое из 20 тел узлов — ~7 мс при ×6, вместе — почти весь кадр; на уровне 6 тела узлов по 2,7–4,5 мс и кнопки HUD (~4,6 мс). Фон и дороги были всего двумя объектами.
- Значит, главное — **число объектов `Graphics` в кадре**, а не их сложность: PF-5 (тела узлов в текстуры) — следующий и самый крупный шаг; затем — `Graphics` кнопок HUD.
- Шум замера большой (одинаковый код даёт 47–73 мс работы кадра в разных прогонах), поэтому сравнения «до/после» делать чередующимися прогонами на одном уровне.

### Итоги PF-5 (2026-11-07)
- **Откуда цена `Graphics`.** В Phaser 4 каждая дуга и окружность (`arc`, `fillCircle`, `strokeCircle`) — 100-угольник (`iterStep = 0.01` в `GraphicsWebGLRenderer`); заливка триангулируется, обводка строится из 100 отрезков со стыками — каждый кадр. Тело узла — десяток окружностей, поэтому оно и стоило ~7 мс при ×6.
- **Тело узла** (`NodeView.drawBody`) рисуется тем же `Graphics` вне списка отображения и запекается в собственную `DynamicTexture` узла при смене ключа тела (владелец, постройка, размер, раскладка); на экране — `Image` на целых пикселях экрана.
- **Запекание — WebGL с суперсэмплингом ×2** (`NODE_VIEW.bodySupersample`): рисуется в 2 раза крупнее и показывается уменьшенным, геометрия и толщина линий — те же, что были. Пробовали canvas 2D, как у фона: края гладкие, но толстые линии canvas рисует иначе (острые стыки «шипами» у короны, после `lineJoin = 'round'` — заметно тоньше обводка) — отказались. Без суперсэмплинга WebGL-текстура — «лесенка» (нет MSAA).
- **Сверка с эталонами:** отличаются только пиксели краёв (больше 64 из 255 по яркости — 11–80 пикселей на снимок, сдвигов и смены цвета нет). Проверены и особые узлы (`dev_stress`, `dev_specials`, башня мага на уровне 10): ничего не обрезано рамкой текстуры (`NODE_VIEW.bodyBox`).
- **Выигрыш:** кадр в 2–2,5 раза быстрее (уровень 6: ~45 → ~20 мс работы при ×6; `dev_stress`: ~170–270 → ~70–100 мс), draw calls почти вдвое меньше.
- **Цена — память видеокарты:** у каждого узла своя текстура в 4 раза больше его площади. Узел радиуса 36 CSS px на экране с DPR 2 — около 1,25 МБ, 20 узлов — ~25 МБ (самые большие узлы — до ~2,7 МБ). Проверить на слабом Android; если окажется много — суперсэмплинг ×2 только при DPR < 2 (на плотных экранах лесенка почти не видна) или общие текстуры для одинаковых тел.
- **Что осталось:** дуга вместимости — второй `Graphics` на каждом своём узле (две окружности = 200 отрезков) — это PF-3, теперь главный оставшийся кусок (`dev_stress`: 44 `Graphics` за кадр, 44–65 мс); затем кнопки HUD.
- Редкое расхождение снимков между прогонами (как на `dev_stress`) один раз было и на уровне 6 (один узел, на глаз не видно), в повторе — совпали.

### Итоги PF-3 (2026-11-07)
- Дуга вместимости запекается так же, как тело (общий класс `src/view/BakedGraphics.ts`: `Graphics` вне списка отображения → `DynamicTexture` ×2 → `Image` на целых пикселях), в свою маленькую текстуру узла. Перезапекается только при смене шага заполнения (по-прежнему 48 шагов), «перебора» (золотая), вместимости, радиуса; у нейтрального узла дуги нет — картинка скрыта.
- Цвет, толщина, старт сверху и прозрачное фоновое кольцо — прежние; сверка с эталонами — как у PF-5 (отличаются только пиксели краёв).
- **Выигрыш:** уровень 6 — ~30 → ~21 мс работы кадра при ×6; `dev_stress` — ~96 → ~29–38 мс; draw calls 45 → 8 на `dev_stress`. Вместе с PF-G и PF-5 кадр на уровне 6 — ~47 → ~21 мс, на `dev_stress` — ~170–270 → ~30–40 мс.
- Счётчик `Graphics.clear` в секунду вырос (больше кадров в секунду — чаще перерисовывается HUD), это не регресс.
- **Что осталось из `Graphics` в кадре:** кнопки HUD (пауза, приёмы) и полоса HUD; на `dev_stress` — ещё по `Graphics` на подсветку выбранного узла и т. п. На уровне 6 `Graphics` теперь ~11 мс из ~21.

**Ограничения замера.** CPU ×6 на настольном процессоре — приближение слабого Android; видеокарта при этом не замедляется. Скриншоты `c01_l06` и `c01_l09` одинаковы побайтово между прогонами; у `dev_stress` состояние на тике 200 изредка различается между прогонами (числа гарнизонов и золото) — причина не найдена (источников случайности в симуляции нет), поэтому для визуальной сверки опираться на реальные уровни.
